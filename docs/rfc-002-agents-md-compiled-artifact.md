## 一、已裁决(采访结论,不再重开)

| # | 问题 | 裁决 |
| --- | --- | --- |
| R1 | 碎片化治理层 | **渲染层治理,存储保持原子**。一条 KN 一个 claim,lifecycle/evidence/regret 精度不变;merge 只用于真重复/被覆盖,不用于「话题相近」 |
| R2 | 域字段 | **`scope.domains` 事实必填**,域词表受控(见 R6)。折叠/下沉/指针行的经济学全部依赖「域是慢变量」 |
| R3 | compiler 新动作 | **rescope**(换布放位置)成为合法编译动作,与 merge/demote/retire 并列。「知识有效但不配全局注意力」不再只有淘汰一条路 |
| R4 | 索引渲染形态 | **分层渲染(a+)**:`project_contract` 整句 claim 留根;有 `scope.paths` 的 `project_knowledge`/`procedure` 下沉到子目录 AGENTS.md 托管段;无路径归属的域折叠为根索引域行 |
| R5 | 平台兜底 | **下沉域在根留指针行**(域名 + 子目录路径,不带 claim)。行数有界于域数;任何平台从根可达全部已发布知识 |
| R6 | 域创建权 | **新域走人审**(`kind: proposal` 队列项),复用现有域自动。裁决前条目暂以无归属域折叠留根 |
| R7 | 散文区所有权 | **翻转:AGENTS.md 整体成为渲染产物**。人供给意图、保留裁决权;人的建议以 `human_decision` 观察进管道,编译后落地,不再直接手改文件 |
| R8 | 散文区源模型 | **三源分治**:代码可导出 section 渲染时从仓库现状现算(零副本);约定/架构 section 从 KN 条目正文渲染;意图 section 只能源于人类裁决条目,人审独占修改权 |
| R9 | 预算模型 | **分级预算**:根与每个子目录托管段各有行数预算。预算的本质是给 compiler 制造「必须减法/rescope」的强制力,每层都需要 |
| R10 | kg 自我定位 | **两层论入宪**(见 §二):台账层是产品,渲染层是耗材 |

## 二、两层论(宪法级定位)

kg 由两层构成,稳定性承诺截然不同:

```text
台账层(产品,承诺稳定,坏了要心疼)
  observation/knowledge schema · authority 分级 · lifecycle 状态机
  · 裁决队列 · evidence/regret 链 · 减法纪律
  价值来源:信息论——意图、被拒方案、裁决依据不记录就永久丢失,
  与 agent 智能水平无关;agent 自治度越高、并发越多,审计与仲裁需求越大

渲染层(耗材,平台代际适配器,预期被整体替换)
  折叠 · 下沉 · 指针行 · 分级预算 · 三源组装 · 锚点管理
  价值来源:伺候当代模型缺陷(上下文有限、注意力稀释、无持久记忆);
  平台原生记忆/长上下文成熟后大半报废——属正常折旧,非设计失败
```

**补丁政策**:渲染层补丁 = 正常损耗,不计为债,不因此怀疑核心命题;
台账层若出现高频补丁(schema/权威分级/生命周期/队列语义反复改),
才是核心命题失效的报警信号。

**失效条件**(诚实记录,到达即重估 kg 存在意义):
① 平台原生提供带人审分级、git 可审计的治理型记忆;
② 宿主项目寿命短、决策密度低、单人供给意图——此时「AGENTS.md 简单手写」
即正确答案,kg 属过度工程。

## 三、AGENTS.md 关注机制(设计依据)

AGENTS.md 不是「每轮读取」,是**会话启动时一次性注入 system context 常驻**:
之后每次推理注意力都要扫过全文。成本公式 = 行数 × 每次推理 × 每个 agent ×
每个任务,与任务是否相关无关。且注意力是竞争性的——规则条数越多,单条被
执行的概率越低(稀释)。

嵌套 AGENTS.md 计费模型不同:根文件一行所有任务付费;子目录文件一行只有
进入该 scope 的任务付费(Codex 合并被触碰子树的 AGENTS.md,Claude Code 对
子目录 CLAUDE.md 按需加载;平台支持度有差异,故有 R5 指针行兜底)。

由此得出根文件准入测试:**「值得让所有任务的每次推理都看到吗?」**
项目目标/命令/结构/技术栈与 contract 类通过;多数 knowledge 类不通过。

## 四、目标形态

```text
根 AGENTS.md(整体渲染产物,分级预算约束)
  ├─ 意图 section        项目目标/优先级——只能源于人类裁决条目,人审独占
  ├─ 代码可导出 section  scripts/目录结构/技术栈——渲染时从仓库现状现算,零副本
  ├─ 约定 section        架构边界/约定——从 KN 条目正文渲染
  └─ kg 索引段
       ├─ 硬规则(.kg/ 读取隔离等)
       ├─ contract 行     project_contract 整句 claim,一条一行
       ├─ 域折叠行        无路径归属域:域名 + 条目号 + 路径
       └─ 指针行          下沉域:域名 → 子目录 AGENTS.md 路径(+条目数)

子目录 AGENTS.md 托管段(各自预算)
  └─ 该 scope 内 knowledge/procedure 的索引行(整句 claim)
```

腐烂防御按源分治:代码可导出内容没有副本故不会腐烂(渲染即现算,
`--check` 模式可机检漂移);条目类走既有管道保鲜;意图类只随人的裁决变。

## 五、治理变更

- **rescope 动作**:撞预算时 compiler 的合法出路从 merge/demote/retire
  扩展为 +rescope(全局行 → 域折叠行 → 下沉 → 仅指针可达)。
- **域词表**:受控词表;新域创建 = `kind: proposal` 人审。防止碎片化在
  域命名层复发(`kyaml`/`kyaml-records`/`kyaml-serialization` 式漂移)。
- **人审边界演化**:RFC-001「托管段之外的 AGENTS.md 变更须人审」在全文件
  接管后自然演化为「渲染模板与 section→源 映射表的变更须人审」;
  机械重渲染(含代码可导出 section 的保鲜刷新)依旧免人审。
- **意图独占**:意图 section 的内容变更永远走人审——agent 无权发明或改写
  项目目标,这是三源分治的不可让渡边界。

## 七、被拒方案(防止未来 agent 重新提案)

| 被拒方案 | 拒因 |
| --- | --- |
| 存储层聚合(多条 KN 合并成厚文档) | claim 退化成主题、生命周期变粗(一节错殃及整篇)、regret/evidence 归属变糊、dedupe 变难。裁决场景:「厚文档一节被证伪时只想动那一节」——原子条目天然满足 |
| 全部按域折叠(含 contract) | contract 的 claim 本身就是规则文本,折叠即未发布 |
| 无兜底下沉(不留指针行) | 不支持嵌套的平台上知识彻底不可发现,「发布即注入」被打穿;指针行成本有界于域数,近乎常数 |
| compiler 自治创建新域 | 无固定模型的 agent 角色划域口味不一致,词表漂移,碎片化换层复发 |
| 散文区纯人养(kg 只提案) | 人天生养不好散文区(写什么/怎么写都纠结,然后腐烂)——人的原话即证据 |
| 一切皆条目(代码可导出事实也抄进 KN) | 制造第二真相源,腐烂从散文搬进条目——「腐烂换了住址,没被消灭」 |
| 只管根的预算 | 无预算的层撞墙报警失效,子目录变知识垃圾场;预算本质是减法强制力,每层都要 |

## 八、风险与开放问题

- **嵌套支持度漂移**:各平台对子目录 AGENTS.md 的加载语义不一且在演进;
  指针行是兜底,但下沉收益随平台而异。渲染层耗材定位(§二)已预期此类重写。
- **域词表冷启动**:首批域怎么定(现有 5 条 active 约可归 2 域)——S2 落地时
  以一次人审裁决初始化词表。
- **预算默认值未裁决**:根收紧到多少、子目录默认多少,留给 S1 实施时以
  dogfood 数据提案 + 人审。
- **三源映射表的宿主差异**:不同宿主的「代码可导出」清单不同(package.json
  vs pyproject),S3 需要 per-host 配置面,警惕在耗材层过度建设。
